# 决策助手证据覆盖修复

本轮以实际可用于选型的字段和场景结果衡量资料质量。发布历史、模型数量、来源数量不当作决策说服力；候选资格也不等于业务效果排名。

## 已修复的证据利用缺陷

功能目录已经声明“编辑仓库文件”覆盖上层“代码编辑工作流”，“运行测试”覆盖上层“工具执行”。原识别逻辑只接受完全相同的功能编号，导致已审核的更具体事实没有满足上层必要条件。

现按既有功能目录的单向关系匹配，并保留原事实和引用。相同 317 条事实下，基础编码工具候选从 Claude Code、Devin 两个变为再包含 Gemini CLI 的三个。没有新增事实，也没有增加性能分数；反向推断、否定描述、未知功能以及循环关系均有回归检查。

账户或产品范围的已审核限制会在候选选择前显示。例如 Gemini CLI 的账户层级说明继续保留，不能将功能资格误当作人人都有可用入口。相同摘要支持多个功能维度时合并呈现并保留全部引用，避免把一句话重复显示成多份证据。已实际核对独立 QA 分析的桌面、手机和打开试用任务流程。

对于已人工审核、官方来源有原文摘录且 90 天内核验的明确分类部署事实，可使用核验时间判断当前可用性，发布日期继续保持未知。这不将采集日伪造成发布日期，也不扩展到数值上下文、许可或价格。报价仍采用独立的 7 天观察门槛。未经审核的新事实不能参与筛选。

## 资料补齐的优先顺序

1. 先修已有证据的解析、字段归一和版本关联，避免重复收录或遗漏已审核内容。
2. 优先消除会卡住整个常见场景的部署与必要功能缺口，再补候选的具体报价、输入输出、上下文、许可及数据条件。先完善每个常用场景的可用候选，避免横向堆满大量只有名称和发布时间的对象。
3. 每条事实绑定具体型号／产品入口、渠道、来源摘录、适用范围和时间。原厂报价、网关余额、订阅费用分别处理；服务使用国家与数据存储地区分别处理。
4. 规格与条款用于筛选资格。公开基准保留测试版本、配置、样本及来源身份；私人业务实测保留实际入口和验收条件。三者分别使用，不能把功能文档包装成用户业务成绩。
5. 每次资料或规则更新后重新计算相同案例，核对原缺项是否消失、是否出现新的冲突，以及保留严格条件的拒绝结果。资料过期仍须重新显现，禁止自动把“维护完成”当成事实补齐。

## 持续审计入口

```powershell
backend/.venv/Scripts/python.exe scripts/audit_decision_coverage.py --output artifacts/decision-coverage/report.json
```

命令只读公开目录，不读取私人记录、不联网、不调用模型。输出每个案例的真实候选和资料维护清单，区分资料整理、用户补条件与业务实测。也可使用 `--snapshot` 指定明确的公开快照。GitHub Quality 在每次检查中运行此命令并保存 `decision-evidence-coverage-<commit>` 工件，便于维护人员处理真实缺口。

审计报告能如实列出阻断项，不将执行成功当成覆盖达标。当前云 API 编码模型场景仍被资料缺项阻断。三条关键新事实已另备待审核包；正式采集在本机因非公网 DNS 被安全策略阻止，保留失败记录，以人工官方网页读取和摘录快照备审，不绕过网络安全策略、不声称完整抓取成功。未审核前不启用。

新资料只有通过既有人工审核及发布流程才能改变公共选型。使用者不需要替所有候选整理资料；维护清单与审核工作由维护端承担。不得因为本次实现了维护审计或修复了一个识别缺陷，就宣布整个知识覆盖或真实选型效果已经完成。

# 决策助手全模块重估与整改执行 Spec

日期：2026-10-16。状态：整改规格已形成，以下实施项尚未按此规格完成验收。

本规格覆盖整个决策助手，而非某张截图或单个空状态。用户最新要求优先于历史“已完成”结论。既有测试、发布记录仍然有效，但只能证明当时列明的工程行为，不能证明新用户理解了建议、获得了选择帮助。实施不以继续扩充匹配词或调整提示文字替代产品改造。

## 1. 产品定位和交付结果

**帮助用户根据自己要完成的工作，选择合适的 AI 产品、模型或实现路线，并知道如何开始使用。**

普通用户可以只说自己的困扰，不必先懂模型/API、定义验收指标、指定候选或整理知识库。专业用户可以输入硬条件并核对依据。两种用户共用事实和判断机制，界面按需求深度展开。

一次有效使用必须产生以下一种结果：

1. 有依据的建议：建议选什么、为什么适合、主要取舍、如何开始。
2. 有价值的分支：存在两个会改变选择的方向，说明差别，让用户点选继续。
3. 明确的限制判断：确实无法满足必要条件，说明冲突和用户可自主选择的替代路线。
4. 明确的资料边界：已知什么、缺什么、这会影响哪一部分判断；仍给出能成立的局部建议。

“补充完整描述”“全部待核验”“先下载任务包”“自己选几个去测”不能作为通用答案。

### 范围

包含 `/ask`、保存后的研究报告、候选比较、条件修改、资料缺口、可选试用、私人记录、判断更新、PDF/Markdown/离线操作说明、登录恢复、桌面/移动端以及对应数据和 API。

保留既有供应商事实审核、访问权限、私人记录隔离和真实效果边界。个人 CCSub 等渠道只影响对应请求。公共页面自动付费调用、多产品 IDE 自动操作、生产环境迁移不作为本次完成条件；既有本地 API 试测能力保留为明确标注的高级功能，不伪装成网页可直接执行。

## 3. 重新设计主流程

### 3.1 入口：先说想完成的事

- 首屏只有任务输入、真实生活场景示例、一个“帮我选择”主操作。
- 示例写成用户问题，例如“我想让同事查询公司的 PDF 文档，回答能找到出处”，不写过时型号对战或技术术语测验。
- “已有工具”“必须满足的条件”可选展开；不强迫填写预算、地区、token 用量或对象类型。
- 已有原始描述与后续补充保持可见、可编辑；不把系统猜测写回为用户原话。
- 一般请求直接给建议；仅当存在影响选择的歧义或硬条件冲突时询问，不再让所有人通过技术条件确认页。
- 登录要求沿用现有安全边界；明确告知何时需要登录，登录前后的输入和选择不能丢失。

### 3.2 理解需求：帮助用户说清楚，而不是退回表单

建立需求摘要：目标、输入材料、希望获得的结果、已有工具、硬条件、偏好、尚不确定项。每项记录来源为用户明确输入、用户选择或可撤销的系统假设。

追问规则：只有答案会改变推荐对象、排除结果或主要下一步，才应追问；每轮一个问题，给 2–3 个易懂选项并允许自由补充/暂不确定。选项不得默认提交。选完在原页继续，不重填、不删除原条件。

| 输入类型 | 应有行为 | 禁止行为 |
| --- | --- | --- |
| “想用 AI 提高办公效率” | 提供整理资料、处理表格、写作等工作方向，用户点选后承接原描述 | 要求用户先写输入、输出、合格标准 |
| “做一个求职助手” | 解释是自己使用现成工具还是开发产品，两条路线的区别；只问这个关键分支 | 默认为 API 或要求理解对象类型 |
| 目标明确，预算未知 | 先按功能与使用门槛给有限建议，费用标待估算 | 因缺 token 数阻断所有建议 |
| 同时提多个工作 | 整理成可并行的任务与组合路线；必要时问先完成哪一项 | 静默只取第一项或让用户重写整题 |
| 超出当前覆盖 | 说明当前能帮助的部分及不支持部分，保留完整原题 | 假装识别成功，随机填候选 |
| 用户说“不知道” | 提供低假设的路线说明或条件分支，保留未知 | 同一句问题循环出现 |

同一未决问题在上下文未变化时不能重复索取；连续两轮仍无法收敛则提供已知条件总结和可选路线，不以机械追问冒充对话。若存在真正决定性的硬条件，必须保留未决状态。

### 3.3 建议：助手承担缩小选择的工作

正常结果首屏依次展示：

1. 一句针对任务的建议，明确是选产品、选模型还是选路线。
2. 2–3 条任务相关理由，标清来自公开事实、使用门槛判断或用户自己的有效记录。
3. 一项真正影响使用的取舍；没有重要取舍就不制造内容。
4. 一个明确主操作，例如“查看上手步骤”“比较这两种方案”或“确认使用方式”。

只有充分依据支持某个方案更符合用户条件时，才指定优先方案。判断顺序：必要条件 → 任务功能适配 → 已有可用工具与切换负担 → 可核验的用户偏好。已有工具不是强制锁定；不符合必要条件时应说明换用理由。

无足够差异证据时，给最多 2–3 个有实质区别的路线/候选，说明如何选；不能按目录顺序、引用数量或自造总分选冠军。没有业务实测时仍可给功能和使用方式层面的建议，但不能声称效果最好。

“是否要换工具”的问题必须得到继续使用、值得考虑替换、或哪项差异尚需确认的直接回答，不能自动转成下载试用任务。

### 3.4 后续操作按需出现

- **查看上手步骤**：适合普通用户。说明去哪里使用、准备什么、第一件做什么；引用已核验的入口，未知入口明确标注。
- **比较备选**：适合有多个选择的用户。只列会改变选择的差异，公共缺项合并一次。
- **验证是否适合我**：可选。先显示可复制的一个小任务及如何判断完成；明确在用户选择的产品执行。
- **记录使用结果**：用户执行后再进入。最少记录先满足有范围的判断；额外指标仅在其影响结论时要求填写。
- **高级 API 试测**：说明执行位置和已具备能力；使用现有授权与限额流程。网页没有执行能力时不显示“开始自动测试”假按钮。
- **保存/导出**：保存建议即可，不要求生成试用记录。任务包改为次级“下载操作说明”，并说明它不会替用户执行任务。

## 4. 证据与知识库：以决策影响管理缺口

“网上没有”“库里没收录”“已有但没命中”“来源过期/冲突”“不适用此型号/渠道”“任务效果未测试”必须分别记录，不能统称“使用条件未确认”。无法证明全网不存在时，禁止声称网上没有。

缺口条目至少包括：候选/型号、要求、已有 Claim/Evidence、缺口类型、影响的决策、影响的常用任务、维护动作、核验时间。前台显示用户能理解的具体句子，例如“当前资料库未收录这个型号的部署说明”，而不是内部审核状态。

执行顺序：

1. 对支持任务提取决定性要求，检查现有已审核资料是否已经足够。
2. 修复实体版本关联、功能映射、召回、时效和渠道边界错误；不得重复采集解决映射问题。
3. 补齐阻断主要建议的官方入口、功能、部署和必要费用/条款依据。
4. 根据受影响任务频率与严重程度排资料队列；普通用户无需承担资料录入或审批工作。
5. 同一任务对比前后分析结果，证明缺口修复改变了正确的判断；仅增加引用数量不算改善。

硬条件缺失：不能宣称满足，可给前提明确的路线。非必要维度缺失：限制对应结论，不阻断无关建议。性能未知：不能比较性能，仍可比较已知功能和接入方式。新事实仍走既有审核；历史批准只适用于原事实和范围。

## 5. 全模块页面与 UI 规格

模式：Operate。沿用 AI Radar 导航、蓝色主色、浅/深色主题与现有组件基础。改造重点是主次关系和交互组织，不把全部标题改成按钮，也不堆叠大色块。

### 页面结构

| 区域 | 默认内容 | 交互 |
| --- | --- | --- |
| 需求条 | 原任务摘要、重要条件 | 轻量“修改”，原页编辑并保留旧结果版本 |
| 建议主体 | 建议、理由、主要取舍 | 一个实心主按钮，次级动作最多两个 |
| 路线/候选对照 | 仅有真实选择差异时出现 | 普通列表或对照表，选中态清楚；不是满屏复选框 |
| 行动区 | 用户已选择的上手或试用步骤 | 主路径无需层层展开；阶段切换保留输入 |
| 依据与范围 | 简短范围说明和来源入口 | 次级文本入口/抽屉；需要长比较时独立面板 |
| 私人记录 | 已有记录摘要，或用户主动进入 | 待测状态不混入建议成绩 |
| 报告操作 | 保存、导出 | 紧凑工具栏；不与建议主按钮竞争 |

### 布局和视觉约束

- 页面标题、主结论、分区标题、候选标题、字段标签形成五级明确层次；使用语义标题，不通过重复粗体模拟层级。
- 建议标题参考 24–28px，分区 20px，子级 16–18px，正文 16px，辅助说明 14px；最终以共享字号体系和实际渲染统一，不逐页散落硬编码。
- 同组元素间距 8–12px，组间 16–24px，主要区段 24–32px；按钮不得因全局段落 margin 出现连续大空白。没有内容的分区不占位。
- 正文使用所属面板可用宽度，不叠加窄 prose/max-width；宽屏如采用两栏，第二栏必须承载真实内容，不能留空。
- 桌面候选对照最多三列；窄屏按相同语义顺序纵向排列。表格长内容自然换行，不裁切型号或横向滚动逃避排版。
- 提示使用小型注释或浅背景说明，主结论使用更强文字层级；风险、错误、未知状态以文字和图标共同表达，不只用颜色。
- 实心按钮用于推进；描边按钮用于次要动作；文本链接用于来源与编辑；展开控件只承载真正可选的成组内容。单行统计直接显示或省略，不折叠。
- 键盘可操作、焦点可见、控件有名称、错误关联字段；触控目标至少 44px，桌面键盘焦点与异步更新均可理解。保持 WCAG AA 对比度。
- 必检 390/768/1440/1920 宽度、深浅主题、中英文长名称、200% 缩放、空结果及全展开状态。页面无水平溢出；正常段落宽度与父内容宽度误差不超过 2px。

## 6. 状态与恢复

| 状态 | 展示与操作 | 数据要求 |
| --- | --- | --- |
| 解析中/分析中 | 可理解的阶段，禁止虚假百分比 | 防重复提交，可取消或安全重试 |
| 需要澄清 | 原页问题、选项、已理解内容 | 保存原题与回答，不静默覆盖条件 |
| 资料不足 | 具体缺口、局部判断、可行下一步 | 区分资料未收录和事实不支持 |
| 全部排除 | 冲突条件和影响 | 仅用户显式修改可放宽硬条件 |
| 请求失败 | 恢复输入并重试 | 错误不伪装成无匹配候选 |
| 修改条件 | 旧建议标记为旧版本 | 保存成功后建立新修订；旧记录不迁成新成绩 |
| 登录过期 | 登录后返回同一任务 | 草稿、选择、任务步骤不丢失 |
| 私人记录变化 | 保存状态与适用范围 | 未保存/未执行内容不得驱动实测结论 |

## 7. 技术落地合同

本节为拟实施设计，不是当前 API 已支持的承诺。

### 统一决策结构

在现有 `DecisionResult` 上增加版本化的可选 `guidance`，旧客户端/历史报告继续兼容。至少包含：

- `schemaVersion`、`outcome`（advice / clarify / conditional / unsupported / blocked）。
- `intent`：任务摘要、多任务、硬条件、偏好、各字段来源与假设。
- `clarification`：问题 ID、触发原因、选项、每个选项的结构化变更、已回答信息；允许自由回答。服务端验证选项属于当前分析。
- `recommendation`：路线/候选、选择理由、取舍、证据 ID、适用前提；同等候选不得强造 primary。
- `unknowns`：缺口分类、是否决定性、受影响结论、恢复路径。
- `nextAction`：类型、目标、执行位置与能力边界；不能仅是文案字符串。

服务器作为决策结果权威；客户端预识别只用于输入提示，不负责另算候选资格。统一状态投影服务 `/ask`、研究详情、比较入口和导出；语言切换不重新产生事实。

先复用现有实体、Claim/Evidence、研究和私人验证记录；禁止复制供应商事实到新 UI 配置。澄清答案和假设随研究修订持久化，API 验证所有新增字段和权限。草稿迁移兼容旧字段，旧报告缺少 guidance 时显示兼容版本并提供重新分析，不能悄悄重写历史判断。

需求理解采用显式条件与规则优先，并提供结构化澄清兜底；本次不能假设存在免费通用语言理解服务。可选模型解析属于后续独立能力，必须具备服务配置、输出校验和失败兜底后才启用，不能取代事实核验。

## 9. 验收矩阵：不能再只凭测试数量宣布完成

以下每项均为核心项。当前均待新规格实施后的证据，不继承旧测试为通过。

| ID | 用例 | 必须证明 |
| --- | --- | --- |
| P01 | 模糊办公需求 | 提供可选方向；点击后继续原题，不返回空表单 |
| P02 | “求职助手”存在使用/开发歧义 | 问一个会改变路线的问题；回答后路线与材料一致 |
| P03 | 明确的常见任务 | 不强制技术确认，直接得到有边界的建议与下一步 |
| P04 | 多任务或表达不在词库 | 能拆解/澄清，不静默丢任务，不靠随机候选填空 |
| P05 | 只有一个已有工具 | 回答是否继续用、什么条件下换；不要求第二账户 |
| P06 | 多个候选依据同等 | 不虚构冠军，提供真实差异或明确同等关系 |
| P07 | 严格离线/隐私限制 | 不暗中放宽；未知与不支持分开 |
| P08 | 预算未知或只需粗略选择 | 未知不视为免费，也不阻断无关功能建议 |
| P09 | 真正需要费用比较 | 价格、渠道、用量、日期范围一致；缺关键输入才追问 |
| P10 | 已有资料未被利用 | 展示映射修复前后差异，不通过复制事实假增覆盖 |
| P11 | 缺项/过期/冲突/效果未测 | 分类准确，不说“网上没有”，不把维护任务强塞给用户 |
| P12 | 用户不知道或拒绝补充 | 不重复同一问题；给可成立的条件分支和明确边界 |
| P13 | 上手与验证 | 明确在哪里执行，复制任务有实际用途，下载可选 |
| P14 | 私人记录 | 保存重开、未测不算通过、账户隔离、修改后判断不陈旧 |
| P15 | 错误与恢复 | 登录/网络失败/重复点击后原题、草稿、修订完整 |
| P16 | 报告与导出 | 页面/PDF/Markdown建议一致，附件无控件垃圾、无孤立标题 |
| P17 | 全页面视觉 | 四个宽度、深浅主题、长内容与全展开通过；无大空洞/窄列提前换行 |
| P18 | 可访问性 | 键盘、焦点、朗读名称、状态反馈、缩放可用 |
| P19 | 未参与开发的问法 | 冻结独立的一批任务后验收；失败不得改预期掩盖 |
| P20 | 建议是否有用 | 从界面可回答“建议什么、为什么、限制是什么、下一步做什么”；内容必须与用户任务对应 |

记录每个案例的输入、条件来源、数据版本、实际结果、截图/操作证据和失败修复。开发者角色走查只能叫工程走查；有真实新用户参与时另记参与情况和实际观察，不虚构研究结论。产品价值评价与事实正确性分别检查，不用“全部有候选”作为答案质量指标。

完成报告逐项给出已验证、未验证、未完成和阻塞项；任何核心项不通过都不能称全模块完成。资料市场覆盖持续演进，但不能以无限扩充全市场资料拖延支持范围内的可用产品交付。

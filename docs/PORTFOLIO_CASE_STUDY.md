# AI Radar 作品集案例

## 项目摘要

AI Radar 把 AI 模型、Agent、框架、论文和 Benchmark 组织成带时间与证据的知识图谱。项目重点不是抓取更多新闻，而是证明一条知识如何被发现、消歧、审核、发布、解释和追溯。

在线预发布由 Cloudflare Workers 前端、Render FastAPI、Neon PostgreSQL 和 Cloudflare Cron 组成。当前公共快照明确标记为 `demo/cached`，包含 49 个实体、23 条 Claim、40 条证据、71 条关系和 55 条时间线。

## 案例一：阻止模型输出直接成为事实

### 问题

模型可以快速抽取事实，但会出现实体歧义、结构化冲突、证据片段缺失和有效时间混淆。若把输出直接发布，知识图谱会变成不可审计的模型缓存。

### 方案

系统使用严格 JSON Schema 抽取、实体别名消歧、语义去重、冲突检测和审核队列。候选与公共快照隔离；只有人工批准，或满足官方原文同时锚定主客体、实体唯一、零冲突等严格条件的关系，才能发布。

### 结果

公开接口不会返回待审、驳回或证据不足候选；每次批准都记录审核者、理由、版本和发布历史。数据增长变慢，但可信边界可以被测试和解释。

## 案例二：把关系图谱从视觉装饰变成查询工具

### 问题

普通节点图容易变成无法阅读的连线动画，用户仍然不知道关系方向、有效时间和证据来源。

### 方案

图谱提供实体筛选、一跳与二跳邻域、最短路径、替代路径、关系方向、可信度、有效时间和来源检查器；移动端同时提供关系列表替代视图。

### 结果

用户可以回答“两个对象如何关联、经过哪些节点、依据是什么、在什么时间成立”，而不是只看到一个可拖动的图。项目因此坚持二维查询界面，没有为了作品集效果加入缺少任务价值的三维场景。

## 案例三：定位自动任务运行但数据不增长

### 问题

线上公开快照一周没有增长，表面上可能是 Cron 未触发、抽取供应商失效、采集停滞或审核链路阻塞。

### 方案

先修复 CI 中遗漏的 Ruff 格式门禁，再通过 Cloudflare 部署记录、线上 schedule、GraphQL Analytics 和实时结构化日志逐层核对，不手工提高频率，也不触发额外模型费用。调度结果继续细分采集、摘要、邮件、抽取和自动批准，并为失败采集新增只包含内部信源 ID 的诊断字段。

### 结果

确认 Cron 使用最新版本并按每小时第 17 分钟运行，抽取供应商仍为已配置和已启用。一次实时周期显示采集 `due=1 / failed=1`、抽取 `planned=0`，因此没有新快照、候选或自动批准内容进入发布链路。问题从“自动任务可能没跑”收敛为“信源采集失败或无内容变化，且当前抽取积压为零”；后续日志可以直接定位失败信源 ID，同时不泄露 URL 参数和凭据。

## 工程结果

- GitHub Quality 工作流同时通过前端、后端、SQLite 与 PostgreSQL 迁移验证。
- 前端覆盖 Lint、类型检查、63 项测试和生产构建。
- 后端覆盖 Ruff、编译检查、Alembic 一致性和 100 余项测试。
- API `/health`、`/ready` 与前端公开地址均可访问。
- 系统保留 Demo 标签，直到 150 条已审核 Claim 和核心关系覆盖真实达标。

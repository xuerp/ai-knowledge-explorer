# AI Radar 产品问题诊断与改进方向

## 执行总结

当前 AI Radar 在技术实现上达标（198条Claim、220条Evidence、测试通过），但**产品价值未能体现**。核心问题：

1. **关系图谱完全空白** - 0条可见关系，用户无法探索知识连接
2. **RAG 问答不可用** - API 返回404，核心交互体验缺失
3. **内容深度不足** - 虽有198条Claim，但多为碎片化的单点事实
4. **产品定位模糊** - 同时想做知识库、图谱、问答，但每个都没做透

**简单说**：你建了一个数据仓库，但忘了给用户提供使用数据的方式。

---

## 一、当前状态（实际测试结果）

### ✅ 技术层面"达标"
- 49个实体（models, agents, frameworks）
- 198条Claim（事实断言）
- 220条Evidence（来源引用）
- 所有测试通过
- 数据质量检查通过

### ❌ 产品层面"不可用"

#### 1. 知识图谱功能完全不可用
```bash
GET /api/v2/graph?entityId=e-claude-code
# 返回: nodes: 0, edges: 0
```

**问题**：
- 虽然数据库有77条关系，但**公开快照中关系数为0**
- 用户看不到任何实体之间的连接
- `/graph` 页面理论上应该是核心体验，实际上是空白

**影响**：
- 产品最大卖点"关系洞察"完全失效
- 用户无法理解 Claude Code vs Cursor，GPT vs Gemini 的关系
- 知识碎片化，没有上下文

#### 2. RAG 问答功能404
```bash
POST /api/v2/ask
# 返回: {"detail": "Not Found"}
```

**问题**：
- API端点不存在或未正确路由
- 前端 `/ask` 页面可能空转或报错
- 黄金问题集（golden questions）无法验证

**影响**：
- "研究助手"体验完全缺失
- 用户只能手动浏览，无法快速获取答案
- 无法展示AI能力的价值

#### 3. 内容质量与深度问题

**Claim 分布不均**：
- Claude Code: 22 claims ✓
- GPT family: ~30 claims ✓
- AutoGen: 1 claim ✗
- CrewAI: 1 claim ✗
- LangGraph: 1 claim ✗

**Claim 类型单一**：
- 60%+ 是 capability, supports, uses 这类描述性事实
- 缺少对比性、演进性、决策性的深度内容
- 例如："Claude Code 支持 MCP" vs "Claude Code 相比 Cursor 的 MCP 集成更完整，支持..."

**实体档案不完整**：
- 0/49 entities 有 versions 信息（虽然字段存在）
- Timeline 只有38条，无法看到技术演进
- 没有"为什么重要""与我何干"的用户视角内容

#### 4. 产品定位混乱

**README 承诺的价值**：
- "持续追踪 AI 技术变化与关系"
- "可验证事实、时间线、关系和研究结论"
- "把分散的官方更新整理成..."

**实际交付**：
- 变化：Timeline 只有38条，不"持续"
- 关系：0条可见关系
- 研究：问答功能404
- 整理：数据存在但用户拿不到

**定位问题**：
- 如果是"知识库"，应该优先完善实体档案的深度与广度
- 如果是"图谱"，应该优先让关系可见可探索
- 如果是"问答"，应该优先保证 RAG 可用
- 现在三个都做了一半，每个都不能用

## 二、根本问题分析

### 问题1：工程驱动而非产品驱动

**症状**：
- 专注于"数据结构正确"（Entity/Claim/Evidence schema）
- 忽略"用户能否用到数据"（API可用性、前端渲染）
- 198条Claim的目标是**数量门槛**，不是**内容质量**

**例证**：
- 关系数据存在数据库中（77条），但快照API返回0
- RAG端点在代码中实现，但路由配置缺失
- 审核系统完善（5通道分类），但待审队列为空（没有生产内容）

### 问题2：自动化优于人工策展

**现状**：
- 依赖自动抽取生成Claim
- 关系回填批次（2026-09-core-relations-02）完成但没产生足够关系
- 审核队列空，说明自动化停滞或效果差

**后果**：
- 内容同质化（都是capability, uses, supports）
- 缺少编辑视角的策展内容
- 核心实体（AutoGen, CrewAI）只有1条Claim，不足以支撑档案页

### 问题3：demo模式的囚徒困境

**当前状态**：
- 数据模式：`demo`
- 快照新鲜度：`cached`
- 原因：核心实体关系覆盖不足（16/16实体 < 5关系）

**困境**：
- 为了去掉demo标签，需要42条关系
- 关系自动抽取已完成但不够
- 手动添加关系需要先有Evidence
- 添加Evidence需要找官方文档
- 找文档、审核、发布的流程太重
- 结果：卡在demo模式，产品看起来"不正式"

**更深层问题**：
即使达到150 claims + 5 relations per core entity的门槛，**产品体验不会本质改善**，因为：
- 关系仍然不可见（快照API问题）
- 问答仍然404（路由问题）
- 内容深度仍然不够（策展问题）

## 三、产品改进方向

### 优先级重排：可用性 > 完整性

#### Phase 1：让核心功能可用（1-2天）

**1.1 修复关系图谱显示** 🔴 Critical
```
问题：公开快照中 relations: []
原因：可能是序列化、权限或API逻辑问题
解决：
  - 检查 /api/v2/snapshot 的序列化逻辑
  - 确保 relations 包含在公开数据中
  - 即使只有10条关系，也应该可见
验收：打开 /graph 页面能看到节点和连线
```

**1.2 修复 RAG 问答** 🔴 Critical
```
问题：/api/v2/ask 返回404
原因：路由配置或前端/后端不一致
解决：
  - 检查 main.py 中 /ask 端点定义
  - 检查 Cloudflare Workers 代理配置
  - 验证 CORS 和认证
验收：输入"What is Claude Code?"能返回结构化答案
```

**1.3 添加"快速开始"体验** 🟡 High
```
当前问题：用户不知道从哪里开始
方案：
  - 首页添加3-5个预置问题卡片（"GPT-5 vs Claude 4 有什么区别？"）
  - 点击卡片直接显示答案+来源
  - 每个答案包含"继续探索"链接到相关实体
验收：新用户30秒内理解产品价值
```

#### Phase 2：提升内容质量（3-5天）

**2.1 人工策展核心实体档案**
```
选择10个最重要的实体（GPT, Claude, Gemini, Claude Code, Cursor等）
为每个实体手工撰写：
  - 完整的summary（200-300字）
  - 3-5个核心能力点
  - 版本演进时间线（至少5个里程碑）
  - 3-5条有洞察的对比关系
  - "为什么重要"一段话

目标：这10个实体的档案能够独立成为有价值的内容
```

**2.2 添加对比视角的Claim**
```
当前：碎片化描述（"Claude Code支持MCP"）
改进：对比性洞察（"Claude Code vs Cursor: MCP集成深度对比"）

类型：
  - 能力对比：A vs B 在 X 能力上的差异
  - 演进对比：A 的 v1 vs v2 关键变化
  - 场景适配：A 适合 X 场景，B 适合 Y 场景

每个核心实体至少2-3条对比性Claim
```

**2.3 完善时间线（Timeline）**
```
当前：38条时间线，不够"持续追踪"的感觉
目标：
  - 每个核心实体至少5个时间节点
  - 最近30天的重要更新（每周至少1条）
  - 标注"重大变化"vs"常规更新"

展示：
  - 首页显示"最近30天的10个重要变化"
  - 实体页面显示该实体的完整timeline
```

#### Phase 3：优化产品定位（1-2天）

**3.1 明确核心场景**

建议选择其中之一作为**主打**：

**选项A：AI技术决策助手**
- 目标用户：技术Leader、架构师
- 核心问题："我应该选择哪个AI工具/模型？"
- 内容重点：对比、评估、场景适配
- 功能重点：问答 > 对比页 > 图谱

**选项B：AI领域知识图谱**
- 目标用户：研究者、分析师
- 核心问题："AI技术生态是如何演进的？"
- 内容重点：关系、演进、全貌
- 功能重点：图谱 > 时间线 > 知识库

**选项C：AI产品追踪器**
- 目标用户：产品经理、从业者
- 核心问题："最近AI圈发生了什么？"
- 内容重点：更新、发布、趋势
- 功能重点：时间线 > 订阅 > 知识库

**当前问题**：三个都想做，每个都不深入

**建议**：选择选项A（决策助手），因为：
1. 市场需求明确（选型焦虑）
2. 你的数据结构已经支持（Claim + Evidence）
3. 差异化明显（其他产品多是新闻聚合或文档索引）

**3.2 重新设计首页**

当前首页传达的信息：
- "我们有很多数据"（49实体、198 Claim）
- "我们很专业"（demo模式、数据质量门槛）

用户想知道的：
- "这能帮我解决什么问题？"
- "我为什么要用这个而不是直接Google？"

建议首页结构：
```
1. Hero Section
   "快速找到可信的AI技术对比和决策依据"
   [3个预置问题卡片，点击直接看答案]

2. 最近更新
   "过去7天的5个重要变化"（带来源和影响说明）

3. 核心对比
   "最常被问到的对比" (GPT vs Claude, Cursor vs Claude Code等)
   [每个对比2-3个要点+完整对比链接]

4. 知识图谱
   "探索AI技术生态全貌"
   [交互式图谱预览，点击进入完整图谱]

5. 关于项目
   （当前内容的浓缩版）
```

## 四、为什么会偏离预期？

### 1. Spec-First vs Product-First

**当前模式**：
1. 写详细的技术spec（REMAINING_ISSUES_RESOLUTION_SPEC.md）
2. 实现所有节点（A-F）
3. 通过所有测试
4. 达到数据门槛（150 claims, 5 relations/entity）
5. （假设）产品就可用了

**问题**：
- 技术完整性 ≠ 产品可用性
- 数据质量门槛是**必要条件**不是**充分条件**
- 用户不关心你有多少条Claim，关心能否解决他们的问题

### 2. 过度工程化

**例子**：
- 5通道审核分类（fresh_safe, duplicate, update, high_risk, invalid）
- 复杂的自动批准规则（6类关系、99%精度门槛、100条复核样本）
- 关系回填批次系统（batch ID, 审计状态, 配额管理）

**后果**：
- 系统复杂度高，维护成本大
- 添加一条关系需要走完整流程
- 自动化失败时无法快速人工补救

**对比**：
- 如果只是手动添加42条关系，2小时就能完成
- 但设计、实现、测试自动化系统花了几周

### 3. Demo陷阱

**初衷**：
- demo模式保证"不成熟的内容不对外"
- 达到门槛后切换到live，展示正式产品

**实际**：
- demo标签让产品看起来"不正式"
- 为了去掉demo标签设置门槛
- 为了达到门槛增加自动化复杂度
- 复杂度导致效率降低
- 门槛一直达不到，一直停在demo

**建议**：
- 去掉demo/live概念
- 用内容质量本身说话（好的内容自然可信）
- 或者demo只是"数据可能不完整"的提示，不是"不能发布"的阻塞

## 六、总结

**当前状态**：技术实现及格，产品体验不及格

**核心问题**：
1. 关系图谱和RAG问答不可用 → 核心体验缺失
2. 内容碎片化、缺少深度 → 用户找不到价值
3. 产品定位模糊 → 不知道为谁解决什么问题

**改进方向**：
1. 立即：修复关系显示和问答功能（让产品能用）
2. 本周：人工策展核心内容（让产品有用）
3. 持续：明确定位，深度优先（让产品好用）

**方法论转变**：
- 从"达到数据门槛"到"解决用户问题"
- 从"自动化优先"到"可用性优先"
- 从"功能完整"到"体验完整"

---

**最重要的一句话**：
不要再问"我还差多少条关系才能去掉demo标签"，而要问"用户能用这个产品解决什么问题，现在能不能解决，如果不能，最快怎么让他们能解决"。

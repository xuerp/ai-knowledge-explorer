# AI Radar 产品现状诊断与改进方向

## 文档定位

- 更新时间：2026-09-04
- 性质：产品判断与优先级建议，不是数据写入或上线授权
- 数据来源：当前仓库、公开 staging 接口、GitHub Quality 和浏览器验收

## 1. 当前结论

AI Radar 不是“核心功能不存在”的半成品。图谱、研究、检索、审核、质量门禁和自动化闭环都已实现。2026-09-04 更新后的核心诉求是把这些能力从平行功能收束为一个产品闭环：追踪器负责发现变化，决策助手负责形成用户价值，知识图谱作为二者共享的可信知识基础设施。

产品可以继续作为 staging 作品集和可信 AI 系统样例展示，但还不能宣称正式 production 或 live 数据服务。

## 3. 产品优势

1. Candidate 与 Verified Claim 分离，模型不直接发布事实。
2. Claim、Evidence、Timeline 和 Relation 共用可追溯证据链。
3. 检索结果保留 Claim ID、Evidence 和降级原因。
4. 支持实体系列、具体版本、生命周期和历史事实。
5. 有真实审核、审计、信源状态、预算和故障恢复边界。

这些能力是产品差异化，应比“拥有多少条数据”更突出。

## 4. 当前真实问题

### P0：发布可信度

- 公开仓库存在疑似凭证文件，需要轮换与仓库清理。
- 自动抽取上限没有在授权批次结束后恢复为 0。
- Render 已运行当前 HEAD，Cloudflare 仍是旧提交。
- 部署没有严格等待前后端全部门禁通过。

这会让用户看到不同版本，也会让失败 CI 的代码进入运行环境。

### P1：核心页面一致性

- 时间线和阅读模式改造仍处于部分迁移状态。
- 模型页还保留旧版“版本演进时间线”，与顶部 Timeline Hero 重复。
- 通用实体页混用 `DensityAwareSection` 和旧 `ReadingModeSection`。
- 自动化前端测试以源码契约为主，对真实渲染和交互覆盖不足。

### P1：信息价值密度

- 旗舰实体内容较深，长尾实体仍可能只有少量 Claim。
- 部分页面同时展示多套时间线、阅读密度和关系入口，信息层级不够统一。
- 关系缺口 42 代表当前覆盖门槛未满足，但不代表必须制造 42 条关系。

### P2：运营可解释性

- 397 条历史驳回全部是 `uncategorized`，原因面板暂时不能指导策略。
- 平均审核耗时受历史迁移数据影响，应补充中位数、P90 和近 7/30 天窗口。
- 评估 cadence 标为 daily，但当前没有每日调度。

### P2：维护成本

- `backend/app/main.py`、`admin.review.tsx` 和 `demo-data.ts` 都超过 3000 行。
- Python 开发工具使用宽版本范围，格式检查可能随解析时间漂移。
- 前端仍使用 Vite 已原生支持的路径插件。

## 5. 产品定位建议

主定位更新为：

> 基于可验证的最新信息理解 AI 变化，并做出模型与产品选择。

功能角色不是三个平行入口：

1. **决策助手：核心价值。** 回答“面对我的任务和约束，我应该先评估谁，依据是什么”。
2. **追踪器：高频入口。** 回答“最近发生了什么，哪些变化值得关注”。
3. **知识库：直接任务入口。** 支持查找实体、版本与已审核事实。
4. **Graph / Relation / Evidence：能力层。** 支撑追踪和决策，不再作为一级产品卖点。

/graph 保留为二级高级探索页，从一级导航移除。实体详情先以可读列表展示开发者、谱系、竞品、生态和来源，再提供“查看完整关系网络”入口。

## 6. 改进顺序

### 第一阶段：恢复可信发布基线

- 处理疑似凭证事件。
- 停止未授权普通抽取。
- 修复当前 UI 回归并补真实交互验收。
- 重构 CI/部署门禁，使前后端运行同一绿色提交。

### 第二阶段：统一核心阅读体验

- 删除模型页重复的旧时间线。
- 完成 ReadingModeSection 到统一密度组件的迁移。
- 通俗模式回答“发生了什么、对我有什么影响”；产品模式回答“用户、场景、竞品与商业变化”；技术模式回答“规格、API、Benchmark、限制与 Evidence”。
- 三种模式共享同一 Verified Claim / Evidence，不复制或改写事实层；差异发生在信息选择、排序和解释层。
- 在桌面和手机上验证时间线、关系、证据和研究入口。
- 增加组件渲染和浏览器行为测试，不只检查源码字符串。

### 第三阶段：分层核心模型与证据深度

- 建立 8–10 个 Core Model Universe；当前先使用已有证据覆盖的 GPT、Claude、Gemini、DeepSeek、Qwen、Kimi、Doubao、ERNIE。
- GPT、Claude、Gemini 为 Anchor Models，优先达到可完整讲述演进路径和支持深度 Compare 的内容密度。
- 其他核心模型达到足以支持 Timeline、横向比较和决策助手的最低信息密度；长尾实体不设条数要求。
- 优先补充能改变决策的官方 Evidence、版本差异、价格、限制和生态关系。
- 只有 Evidence 明确支持时才新增关系或比较结论。
- 15–25、8–15 等数字只能作为观察范围，不能成为写作配额；某个模型只有 7 个高价值事件时不得凑到 10 个。

### 第四阶段：做深决策助手

- 输入应显式包含任务、优先级、预算、部署和不可接受条件。
- 输出应给出有条件的建议、备选方案、适用边界、信息时点和直接 Evidence。
- Compare 作为结构化分析工具嵌入决策流程，而不是与决策助手争夺一级入口。
- Evidence 不足时缩小结论或拒答，不生成看似完整的推荐。

### 第五阶段：验证正式产品方向

- 用 5–10 位目标用户完成任务测试。
- 记录任务完成率、找证据耗时、拒答是否清楚和比较是否帮助决策。
- 根据反馈决定优先扩展研究、实体档案、关系探索或订阅。

## 7. 禁止采用的捷径

- 不硬编码关系、答案或动态以制造“产品可用”的外观。
- 不为了去掉 Demo 标签而补造关系。
- 不删除 Candidate/Verified、Evidence 或 live gate 边界。
- 不把错误 API 返回的 404 当作功能不存在的证据。
- 不把 staging 称为 production，也不把部署启动称为部署完成。

## 8. 产品验收问题

每次迭代优先回答：

1. 用户能否在 30 秒内理解产品解决什么问题？
2. 用户能否找到结论对应的 Claim 和 Evidence？
3. 用户能否分辨当前事实、历史事实、推断和未核验内容？
4. Evidence 不足时，系统是否明确拒答？
5. 同一页面在桌面和手机上是否提供相同核心能力？
6. 部署页面是否与已通过 CI 的精确提交一致？

只有这些问题有真实验收记录，产品体验才算完成。

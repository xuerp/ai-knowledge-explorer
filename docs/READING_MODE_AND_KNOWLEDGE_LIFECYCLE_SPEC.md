# AI Radar 阅读模式与知识生命周期治理 Spec

## 0. 文档信息

- 文档状态：实施中；阶段 A、B、D 已完成，阶段 C 存量处理与阶段 E、F 待实施
- 优先级：P0 产品可信度与信息架构
- 适用版本：作品集版本完成后、正式数据质量门槛验收前
- 依赖能力：Entity、Claim、Evidence、Timeline、Relation、审核队列、发布历史、信源采集与数据质量接口
- 不依赖外部资源的部分：阅读模式、确定性去重、事实版本关系、审核交互、历史分页和存量队列分析
- 需要单独确认费用的部分：新增自动信源启用后产生的外部模型抽取、使用外部嵌入或重排模型进行存量语义聚类

## 1. 背景与问题

AI Radar 已具备中文与英文、明暗主题和“通俗 / 产品 / 技术”偏好，但当前阅读模式只完成了偏好持久化：顶部入口可以切换，设置页可以保存，模型页底部会显示模式名称，主体内容并不会随模式发生实质变化。

这会造成三个问题：

1. 用户看到阅读模式入口后，会合理预期正文重点、解释深度或默认展开内容发生变化；当前行为与预期不符。
2. 演示脚本和既有文档把阅读模式描述为已实现能力，存在产品叙事超过真实能力的风险。
3. 已审核事实持续增长后，即使展示层已经改成“最近 5 条 + 历史归档”，重复、替代和过时事实仍可能同时占据当前摘要。

因此，本轮不能只美化下拉菜单，而要同时完成两层治理：

> **同一份可信知识按角色重新编排 + 同一主题事实按生命周期合并、替代和归档。**

## 2. 当前基线

### 2.1 已实现

- 阅读偏好支持 `general`、`product`、`technical` 三种值，并保存在当前设备。
- 顶部入口会显示当前模式，桌面菜单和设置页共用同一份名称与说明配置。
- 模型和其他实体页会按模式确定性调整导读、场景、限制、档案、关系、时间线和证据的顺序。
- 技术模式默认折叠使用场景，缺少模式专用文案时继续使用原始已审核事实。
- 实体页默认展示最近核验的 5 条事实。
- 每条事实的直接证据默认折叠。
- 其余事实进入历史区，前端每次加载 10 条。
- LLM 只能产生候选事实，不能直接进入公共知识库。
- 公开事实与待审核事实已经有确定性语义指纹、冲突检测和证据隔离基础。
- 自动任务每 30 分钟唤醒一次，但抓取和抽取仍受信源周期、内容 Diff 和单周期上限约束。

### 2.2 尚未实现

- 大多数 Claim 没有完整的通俗、产品和技术三套解释文本。
- 公开事实缺少明确的“当前 / 已替代 / 历史”生命周期字段。
- 审核员缺少“合并证据”“替代已有事实”的明确操作。
- 存量数百条候选尚未形成可重复执行的去重、陈旧度和优先级清理流程。
- 单实体事实继续增长后，公共接口尚未提供游标分页。

## 3. 产品目标与非目标

### 3.1 产品目标

- 三种阅读模式必须产生用户可感知、可测试的内容编排差异。
- 三种模式共用同一组 Claim 和 Evidence，不维护互相冲突的三套事实。
- 模式切换即时生效，不刷新页面，不丢失当前实体和滚动上下文。
- 当前事实摘要只保留仍然有效、重要且非重复的事实。
- 同一事实的新证据合并到已有事实，而不是新增相似卡片。
- 同一主题值发生变化时，新事实替代旧事实，旧事实进入历史且保持可追溯。
- 审核后台能够批量处理确定性重复项，同时把价格、日期、可用性和评测等高风险变化留给人工判断。
- 清理旧队列后，再逐步启用稳定的官方机器入口，避免新增内容继续堆积在旧问题之上。
- 所有阶段通过自动化测试、完整质量门禁和线上验收。

### 3.2 非目标

- 不让模型为每条事实即时生成三套改写。
- 不因切换阅读模式改变事实真值、置信度、有效期或证据。
- 不自动删除已发布事实、证据、审核记录或发布历史。
- 不把社区传闻自动提升为正式事实。
- 不绕过登录、验证码、付费墙、网站防护或安全采集限制。
- 不为了展示效果提前切换 `AI_RADAR_DATA_MODE=live`。
- 未经确认不提高单周期抽取上限，不启用会增加外部模型费用的新批量任务。

## 4. 用户与核心任务

### 4.1 通俗阅读者

目标是快速知道“它是什么、发生了什么、为什么重要”。用户不应先看到密集参数、全部关系边或长证据列表。

### 4.2 产品阅读者

目标是判断“适合什么场景、带来什么机会、有哪些限制和风险、与替代方案有什么差异”。用户需要优先看到用例、变化、限制和对比入口。

### 4.3 技术阅读者

目标是核对“架构、API、上下文、价格口径、Benchmark、关系与原始资料”。用户需要更快进入结构化规格、指标、关系、时间线和证据。

### 4.4 审核员

目标是把候选判断为新事实、重复证据、已有事实更新、冲突或证据不足，而不是只做批准和拒绝二选一。

## 5. 阅读模式产品规则

### 5.1 共同事实层

三种模式必须读取同一 Entity、Claim、Evidence、Timeline 和 Relation。模式只允许改变：

- 区块顺序；
- 默认展开或折叠状态；
- 摘要文案选择；
- 指标、证据和关系的默认展示密度；
- 引导按钮和推荐下一步。

模式不得改变：

- Claim 是否已审核；
- Evidence 是否支持或反驳；
- Confidence；
- 有效期；
- 来源地址；
- 数据模式标签。

### 5.2 顶部入口

桌面端顶部入口必须显示当前模式，而不是只显示书本图标：

- `通俗`、`产品` 或 `技术`；
- 保留模式图标；
- 展开后每个选项显示名称、单行说明和明确选中标记；
- 切换成功后菜单关闭，当前页面立即重新编排；
- 键盘可聚焦，方向键可选择，回车或空格可确认；
- 入口提供中文和英文无障碍名称。

移动端不在顶部增加模式入口，统一通过“设置 → 阅读模式”修改，避免挤压返回、Logo 和账户入口。

### 5.3 三种模式的实体页编排

| 内容区块     | 通俗模式               | 产品模式                   | 技术模式                        |
| ------------ | ---------------------- | -------------------------- | ------------------------------- |
| 知识导读     | 第一优先，保留术语解释 | 简化为定位和用户价值       | 简化为技术定义                  |
| 为什么重要   | 默认展开               | 默认展开并靠前             | 保留但降低优先级                |
| 使用场景     | 展示代表性场景         | 第一优先，完整展示         | 默认折叠                        |
| 限制与风险   | 通俗解释               | 第一优先，完整展示         | 聚焦技术边界和证据口径          |
| 当前事实摘要 | 最近 5 条，紧凑展示    | 优先变化、可用性和定位事实 | 优先规格、架构、评测和 API 事实 |
| 规格与指标   | 摘要或折叠             | 展示影响决策的指标         | 默认完整展开                    |
| 版本谱系     | 展示关键版本           | 突出版本选择差异           | 展示完整结构化规格              |
| 关系         | 展示主要一跳关系       | 突出竞争、生态和开发者关系 | 展示关系类型、方向和证据        |
| 时间线       | 展示关键事件           | 突出发布、下线和价格变化   | 展示完整事件与来源              |
| Evidence     | 默认折叠               | 默认折叠，显示来源数量     | 显示来源类型、日期和原始入口    |

### 5.4 文案选择规则

第一阶段不生成新的模式文案，使用现有结构确定性编排：

- 通俗模式使用现有 `summary`、`knowledge.introduction` 和 `significance`。
- 产品模式优先使用 `knowledge.useCases`、`limitations`、`changes` 和比较维度。
- 技术模式优先使用 `specs`、`metrics`、Relation、Timeline 和 Evidence。
- Claim 若存在 `text.technical`，技术模式使用该文本；否则回退到普通 Claim 文本，并明确沿用原始审核事实。
- 不允许因缺少模式专用文案而调用模型即时补写。

### 5.5 模式持久化与路由

- 当前设备继续使用本地偏好存储。
- 模式切换不得修改当前路径和查询参数。
- 新标签页默认读取已保存模式；无偏好时使用通俗模式。
- SSR 首屏以通俗模式安全渲染，客户端加载偏好后只重新编排内容，不发起新的知识数据请求。
- 跨标签页的偏好变化继续通过存储事件同步。
- 清除浏览器数据后回到通俗模式。

### 5.6 空状态与降级

- 某实体没有规格、指标或用例时，不展示空区块。
- 技术模式缺少技术专用文本时，显示已审核普通文本，不展示伪造占位内容。
- 产品模式缺少使用场景时，展示“当前证据不足以形成产品场景结论”，并提供证据或研究入口。
- 模式偏好读取失败时回退通俗模式，页面仍可使用。

## 6. 事实生命周期产品规则

### 6.1 生命周期状态

公开 Claim 增加以下逻辑状态：

- `current`：当前有效，可进入实体摘要和研究检索。
- `superseded`：已被新事实替代，仅进入历史和时间线。
- `historical`：仍有研究价值，但不代表当前状态。
- `retracted`：证据被撤回或审核纠正，不进入普通回答，保留审计记录。

初期可以由现有有效期和替代关系计算状态；数据库迁移阶段再持久化必要字段。

### 6.2 候选与已有事实的四种关系

1. **重复事实**：主实体、谓词、标准化值和有效期相同。行为是合并新证据，不新增公共 Claim。
2. **事实更新**：主实体和谓词相同，但值或有效期发生变化。行为是批准新事实并把旧事实标记为已替代。
3. **补充事实**：描述不同维度，不能被已有事实覆盖。行为是创建新 Claim。
4. **冲突事实**：有效期重叠且值互斥。行为是进入冲突审核，不允许批量批准。

### 6.3 当前摘要选择

实体页“当前事实摘要”只选择：

- 生命周期为 `current`；
- 已审核；
- 至少一个可解析 Evidence；
- 不与更高优先级事实重复；
- 有效期未结束；
- 按重要性、变化新鲜度、证据质量和最近核验时间排序。

默认最多 5 条。其余当前事实和所有历史事实仍可进入历史区、搜索、研究与引用。

### 6.4 重要性规则

第一阶段使用确定性规则，不调用外部模型：

- 发布、下线、价格、上下文、可用性、核心能力和安全事件优先级较高；
- 公司使命、团队构成等稳定背景事实优先级中等；
- 同一来源、同一天、同一实体的近义背景描述降低展示优先级；
- 社区线索、证据不足或缺少有效期的易变事实不能进入当前摘要；
- 人工审核员可以覆盖展示优先级，但必须记录理由。

## 7. 审核后台改造

### 7.1 审核动作

每条候选至少提供以下明确动作：

- 批准为新事实；
- 合并为已有事实的新证据；
- 批准并替代已有事实；
- 标记需要更多证据；
- 拒绝；
- 跳过并保留待处理。

“合并”和“替代”必须先选择目标 Claim，后端再次校验实体、谓词、有效期、版本和并发状态。

### 7.2 相似事实提示

审核卡片显示最多 3 条相似项：

- 已发布相似事实；
- 待审核相似候选；
- 可能冲突的事实。

每条提示展示相似原因、状态、有效期、证据数量和目标 Claim。模型自报置信度不得作为自动合并依据。

### 7.3 批量边界

允许批量执行：

- 确定性指纹完全相同的待审核项合并；
- 同一候选的重复证据合并；
- 已被相同目标替代且无并发变化的幂等确认。

禁止批量执行：

- 价格、日期、可用性、上下文和评测成绩的值更新；
- 任何冲突项；
- 社区来源；
- 实体消歧不唯一；
- 有效期重叠但值不同。

## 8. 存量队列清理方案

### 8.1 只读盘点

先生成不修改数据的盘点报告：

- 开放候选总数；
- 按实体、来源、创建月份和风险分布；
- 确定性重复组数量；
- 可能更新组数量；
- 冲突组数量；
- 缺证据和证据锚点无效数量；
- 超过 90 天的陈旧候选数量；
- 与已发布事实重复的候选数量。

报告不得包含凭据或带敏感参数的完整 URL。

### 8.2 清理顺序

1. 合并确定性重复证据。
2. 关闭已经发布且语义指纹相同的重复候选。
3. 集中处理同一实体、同一来源、同一天的近义背景事实。
4. 人工判断事实更新和冲突。
5. 对超过 90 天且涉及易变字段的候选重新核验证据。
6. 缺证据、来源不可达且无法补证的候选标记为需要更多证据或拒绝。
7. 最后处理低风险稳定背景事实。

### 8.3 安全要求

- 清理前生成数量基线和可重复执行的 Dry Run。
- 每批最多 50 条，与现有审核事务上限一致。
- 每批记录操作人、理由、输入版本和结果。
- 重复执行不得再次修改已经合并的候选。
- 不使用数据库脚本绕过审核服务直接发布 Claim。
- 不删除 Evidence、审核历史或发布历史。

## 9. 信源与新鲜度接续方案

队列清理完成前，不盲目增加大量信源。接续顺序如下：

1. 保持已熔断永久失败源停止重试。
2. 保持人工证据页只用于溯源，不伪装成自动入口。
3. 优先验证无需登录、体积可控的官方 Markdown、JSON、RSS、更新日志和代码仓库。
4. 新信源先登记为关闭状态，完成白名单、安全预检和首次快照验证。
5. 只有内容确有变化时进入抽取。
6. 先启用一个来源，观察至少两个 Cron 周期，再扩展下一批。
7. 任何会增加外部模型调用的启用动作必须单独确认。

## 10. 数据结构与接口设计

### 10.1 Claim 建议字段

- `lifecycleStatus`：当前、已替代、历史或撤回。
- `supersedesClaimId`：新事实替代的旧 Claim。
- `supersededByClaimId`：旧事实指向新 Claim，可由关系反查或冗余存储。
- `topic`：能力、价格、版本、组织、评测、生态、可用性或安全等主题。
- `displayPriority`：人工可覆盖的展示优先级。
- `lastReviewedAt`：最近人工核验时间。

字段命名以最终数据库和 API 约定为准，迁移必须向前兼容。

### 10.2 审核 API

新增或扩展审核决策类型：

- `approve-new`；
- `merge-evidence`；
- `approve-superseding`；
- `needs-more-evidence`；
- `reject`。

合并和替代请求必须包含：

- 目标 Claim ID；
- 候选版本；
- 目标 Claim 当前版本；
- 审核理由；
- 幂等键。

### 10.3 公共查询

第一阶段继续兼容公共快照。单实体事实增长后增加：

`GET /api/v2/entities/{entityId}/claims`

建议参数：

- `scope=current|history|all`；
- `topic`；
- `cursor`；
- `limit`，默认 20，最大 100；
- `sort=priority|verifiedAt|validFrom`。

响应必须包含下一页游标和总量提示，但不得泄露待审核、驳回或证据不足候选。

## 11. 指标与质量门槛

### 11.1 阅读模式指标

- 三种模式切换后，实体页至少两个区块的顺序或默认展开状态发生可测试变化。
- 切换不触发新的知识请求。
- 刷新后偏好保持。
- 首页和移动端顶部不出现拥挤或布局跳动。
- 无专用文案时正常回退，不出现空白或模型生成占位。

### 11.2 审核治理指标

- 确定性重复候选不再新增公共 Claim。
- 新证据可以合并到已有 Claim，并进入审计记录。
- 替代事实发布后，旧事实不再进入当前摘要。
- 冲突事实不能通过批量安全路径发布。
- 存量清理前后数量可对账，Evidence 和发布历史不丢失。
- 新候选不再被旧积压遮蔽，开放队列支持按新鲜度和风险排序。

### 11.3 Live Gate 保持不变

- 至少 150 条真实已审核 Claim；
- 核心实体关系覆盖达到要求；
- 20 个黄金问题至少 85% 通过；
- 无缺失 Evidence 的公开 Claim；
- 生产就绪检查通过；
- `liveReady=true` 前继续保持 `demo`。

## 12. 实施阶段

### 阶段 A：阅读模式真实性（已完成）

- 重构顶部阅读模式入口，显示当前模式和说明。
- 建立共享模式配置，不在各页面复制条件判断。
- 实体页按模式调整区块顺序、密度和默认展开状态。
- 设置页与顶部入口使用同一配置。
- 修正文档和演示脚本中超过真实能力的描述。

已通过共享配置、实体页区块重排、技术模式场景折叠和自动化契约测试实现；不依赖外部账号或模型费用。

### 阶段 A.2：阅读模式语义视图（已完成）

阶段 A 的区块重排不足以让用户感知三种模式的真实差异，因此继续完成以下改造：

- 通俗模式只展开定义、重要性、关键事实、关键版本、关键时间和推荐问题，隐藏规格表、关系图、对比表与原始证据列表；
- 产品模式使用独立的“产品决策视图”，完整展示产品价值、使用场景和采用限制，并展开版本选择、竞品关系、变化与对比；
- 技术模式使用独立的“技术定义与证据口径”，展开规格、指标、关系、时间线和原始来源，默认收起非技术使用场景；
- 当前事实按模式进行确定性语义排序：产品模式优先价格、可用性、发布和成本等事实，技术模式优先 API、架构、上下文、评测和工具等事实；
- 技术模式在 Claim 存在 `text.technical` 时使用技术文本，否则沿用已审核原文；
- 每个实体页明确显示当前模式与聚焦范围，切换模式不会重新请求知识数据，也不会改变事实真值和证据关系；
- 信息不足时使用明确空状态，不调用模型即时补写。

这一阶段不要求为每条事实生成三套新文案。当前公开事实规模已经足够支持确定性分流；后续可在抽取 Schema 中逐步补充产品影响、技术机制和适用对象等结构化字段，提高分流精度，但不作为本阶段上线阻塞项。

已通过向前迁移、审核记录生命周期字段、合并证据与替代事实事务、双版本校验、幂等键和公共快照过滤实现。重复事实只向目标事实补充去重后的 Evidence；替代操作保留旧事实审核记录并建立双向指向，但公共快照只返回当前事实。实现和验证均未调用外部模型。

## 13. 自动化测试要求

### 13.1 前端

- 顶部入口显示当前模式。
- 三种模式配置完整且互斥。
- 设置页与顶部入口写入同一偏好。
- 模式切换不改变路由和底层 Claim 数量。
- 通俗、产品、技术模式的区块顺序符合矩阵。
- 缺少规格、指标、用例或技术文本时正确降级。
- 当前摘要默认 5 条，Evidence 默认折叠。
- 历史区每次加载 10 条且不会遗漏记录。
- 桌面和移动导航无溢出。

### 13.2 后端

- 重复事实只合并 Evidence，不新增 Claim。
- 替代事实建立双向可追溯关系并更新有效期。
- 冲突事实拒绝批量批准。
- 合并和替代请求校验候选版本、目标版本和幂等键。
- 同一请求重复提交返回相同结果。
- 已替代和撤回事实不进入当前公共查询。
- 历史查询游标稳定、无重复、无遗漏。
- 待审核和驳回内容不泄露到公共接口。
- 存量 Dry Run 不修改任何数据。

### 13.3 完整质量门禁

每批修改必须执行与 `.github/workflows/quality.yml` 一致的检查：

1. 前端锁文件安装验证；
2. 导出演示快照并确认无差异；
3. 前端 Lint、类型检查、测试和生产构建；
4. Cloudflare staging 配置生成验证；
5. Ruff 格式、Lint 和 Python 编译；
6. SQLite Alembic upgrade、current 和 check；
7. PostgreSQL 迁移验证；
8. 后端完整测试。

## 14. 线上验收场景

### 场景一：阅读模式切换

1. 打开 GPT 或 Anthropic 实体页。
2. 记录通俗模式的前两个内容区块。
3. 切换产品模式，确认使用场景和限制上移。
4. 切换技术模式，确认规格、指标和证据上移。
5. 刷新页面，确认模式保持。
6. 打开新标签页，确认使用相同偏好。

### 场景二：证据合并

1. 创建与已发布 Claim 指纹相同、Evidence 不同的候选。
2. 审核后台提示已有事实。
3. 选择“合并为新证据”。
4. 公共 Claim 数量不增加，Evidence 数量增加，审计记录可查。

### 场景三：事实替代

1. 创建同实体、同谓词但新值不同的候选。
2. 选择“批准并替代已有事实”。
3. 新事实进入当前摘要。
4. 旧事实进入历史并指向新事实。
5. 时间线能够解释变化发生时间。

### 场景四：存量队列清理

1. 运行 Dry Run 并记录各分类数量。
2. 对一组确定性重复项执行 50 条以内批处理。
3. 再次运行 Dry Run，确认数量按预期下降。
4. 公共 Claim、Evidence、审核历史和发布历史可对账。

### 场景五：异常与回滚

1. 模拟模式偏好损坏，确认回退通俗模式。
2. 模拟合并目标并发更新，确认返回冲突而不是覆盖。
3. 模拟 Cloudflare 旧前端访问新 API，确认向前兼容。
4. 必要时关闭新 UI 操作入口，但不回滚或删除已经迁移的数据。

## 15. 发布与回滚策略

1. 阅读模式配置和 UI 可以独立发布，无数据库变更。
2. 生命周期字段先发布后端迁移和兼容读取，再发布写入逻辑。
3. 审核前端只在 API 能力健康后开放合并和替代按钮。
4. 公共分页接口上线后，旧快照接口至少保留一个发布周期。
5. 新信源逐个启用，不批量同时开启。
6. 回滚优先关闭新入口或功能开关，不删除已生成的审计、证据和版本关系。

## 16. 外部决策边界

以下工作可以直接推进：

任何 API Key、邮箱密码和云平台密钥都不得通过聊天发送，也不得输出或覆盖 `backend/.env`。

## 17. 完成定义

只有同时满足以下条件，本 Spec 才算完成：

- 阅读模式在实体页产生真实、稳定且可解释的内容编排差异；
- 顶部入口能识别当前模式，移动端布局无拥挤；
- 三种模式共用同一事实与证据层；
- 重复候选能够合并 Evidence；
- 更新候选能够替代旧 Claim，历史仍可追溯；
- 冲突和高风险更新继续保留人工审核；
- 存量队列完成 Dry Run、分批清理和数量对账；
- 单实体事实支持可扩展历史查询；
- 新信源启用遵守安全和费用边界；
- 所有前后端测试、迁移、CI、预发构建、桌面和移动验收通过；
- 正式质量门槛未通过前继续保持 `demo`。

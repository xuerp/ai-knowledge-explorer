# AI Radar 关系本体

版本：1.0.0

生效日期：2026-08-31

> 本体用于限定关系类型的合法取值范围，不代表任意两个核心实体之间都应存在其中某种关系。缺失关系不是必须补齐的缺口，而是可能反映了两个实体之间确实没有值得记录的关系。

## 使用边界

- 本体是发布约束，不是关系数量配额；既有质量规则中的“距 5 条差值”只能作为覆盖观测值。
- 新关系必须由官方第一方 Evidence，或论文、基准测试等一手材料直接支撑。Evidence 必须同时锚定主语、宾语和关系语义。
- 新关系 Claim 一律先进入人工审核；Epic 2A/2B 执行期间必须保持默认的 `AI_RADAR_AUTO_APPROVE_GROUNDED_RELATIONS=false`，不得为关系补齐批次开启自动批准。人工审核不得因为覆盖差值而降低证据标准。
- `verified` 是新关系发布的最低置信度。既有 `inferred` 关系作为历史数据保留并在诊断中如实计数，但不能作为新增关系的验收模板。
- 关系端点必须唯一解析为目录中的两个不同实体；Evidence 引用必须完整解析。
- 本体只采用仓库实际支持的 kebab-case 谓词。Spec 示例中的下划线写法是概念名，不是 API 合法值。

## 合法关系类型

| 合法谓词          | 方向与语义                                            | 是否允许多值 | 新发布最低置信度 | 证据要求                                                                 |
| ----------------- | ----------------------------------------------------- | ------------ | ---------------- | ------------------------------------------------------------------------ |
| `developed-by`    | 产品、模型、工具 → 开发组织                           | 是           | `verified`       | 第一方产品页、官方仓库或组织公告明确说明开发方                           |
| `based-on`        | 派生实体 → 明确的基础技术、模型、论文或框架           | 是           | `verified`       | 一手材料明确使用“基于/构建于”等依赖语义，不能从相似性推断                |
| `competes-with`   | 实体 ↔ 实体；语义对称，存储时端点按 ID 规范化         | 是           | `verified`       | 官方对比、共同基准的一手说明或双方可核验定位；市场类别相同本身不构成关系 |
| `benchmarked-on`  | 被评测对象 → 基准、数据集或评测                       | 是           | `verified`       | 官方技术报告或基准一手结果明确给出对象和基准                             |
| `uses`            | 使用方 → 被使用的模型、协议、框架、API 或工具         | 是           | `verified`       | 官方架构或产品文档明确说明实际使用，不从兼容性推断                       |
| `cited-by`        | 被引用论文或资料 → 引用它的论文、模型或实体           | 是           | `verified`       | 论文正文、参考文献或官方技术报告可直接定位引用关系                       |
| `part-of`         | 成员、具体版本或组件 → 所属系列、产品或组织结构       | 是           | `verified`       | 官方目录、版本页或架构文档明确说明归属                                   |
| `successor-of`    | 较新版本或替代产品 → 被继任的较旧版本或产品           | 是           | `verified`       | 官方发布说明明确给出演进或替代关系；发布时间先后本身不充分               |
| `integrates-with` | 提供或实现集成的一方 → 被集成的协议、平台、工具或服务 | 是           | `verified`       | 官方集成文档明确说明集成主体、目标及可用方式；与 `uses` 不可仅凭措辞互换 |

## 规范化与去重

- `competes-with` 是当前唯一按无方向语义去重的类型，规范键为排序后的端点加谓词和有效期。
- 其余类型均保留方向，规范键为 `fromId + kind + toId + validFrom + validTo`。
- 同一规范键再次出现时，只允许合并新的有效 Evidence，不新增平行边。
- `successor-of` 不使用传递闭包制造边；A 继任 B、B 继任 C，不自动生成 A 继任 C。
- `integrates-with` 保留方向，因为“产品 A 提供 B 集成”不等于“B 提供 A 集成”。

## 不属于当前本体的概念

原 Spec 示例还出现 `acquired`、`succeeded_by`、`partners_with`。当前仓库没有这些谓词的完整 schema、方向规则、去重逻辑和发布链路，因此它们不是 v1.0.0 的合法值：

- “继任”统一使用现有的 `successor-of`，不新增语义相反的 `succeeded-by`。
- 收购和合作关系在完成独立证据标准、时间有效性与冲突处理设计前不得用自由文本谓词发布。

## 审核不变量

人工审核至少核对：端点唯一解析、关系谓词属于本体、原文同时出现两端实体、原文存在对应关系语义、Evidence URL 与信源记录一致、语义指纹不重复、有效期不冲突。任一条件不满足时保持待补证或拒绝，不发布关系。

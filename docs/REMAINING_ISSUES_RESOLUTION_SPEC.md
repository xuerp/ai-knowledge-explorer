## 1. 背景与结论

AI Radar 的产品闭环、公开演示、审核后台、信源治理、知识生命周期、全文检索 RAG 和 GitHub 公开仓库已经建立。当前最主要的问题已经不是“缺少更多页面”，而是以下六条链路仍未同时达到可持续运行标准：

1. 公开数据数量已经增长，但“公开 Claim”“已批准 Claim”“人工核验 Claim”仍缺少统一统计口径。
2. 公开 Claim 中仍存在实体关联缺失，核心实体关系深度不均衡。
3. 审核队列有历史积压；确定性重复、可能更新、冲突和无效证据不应采用同一种处理方式。
4. 部分信源处于手动、重试、冷却或自动熔断状态，最新内容获取仍不稳定。
5. RAG 已经具备引用和降级边界，但召回率不足，阅读模式也因高质量事实分布不均而难以体现差异。
6. `demo/cached` 仍是正确状态；在数据质量、黄金问题、运行保障和外部资源未真实验收前不能切换 `live`。

本 Spec 的核心结论是：

> 下一阶段不继续横向增加功能，而是纵向打通“新鲜官方来源 → 可审核候选 → 已关联事实 → 核心关系 → 可检索回答 → Live Gate”闭环。

## 4. 目标与非目标

### 4.1 目标

1. 用一个可复现报告统一公开快照、数据质量、审核队列、黄金问题、RAG 和运行状态。
2. 修复所有当前公开 Claim 的实体关联，并阻止新的无实体 Claim 发布。
3. 在不删除历史记录的前提下，对审核积压进行分层、分批和可对账处理。
4. 让自动熔断、手动采集、瞬时失败和永久失败信源各自进入正确状态。
5. 优先使用官方 Markdown、JSON、RSS、原始代码仓库等机器入口恢复内容新鲜度。
6. 在零额外模型费用前提下显著提高 PostgreSQL 检索召回。
7. 补齐核心实体关系，使阅读模式、图谱和研究回答具有真实差异。
8. 只有所有机器门槛和人工验收同时通过后才允许讨论 `live`。

### 4.2 非目标

- 不把所有待审核候选直接批量批准。
- 不为达到 150 条门槛硬编码或复制 Claim。
- 不让 LLM 直接写入公开知识库。
- 不把采集时间、审核时间当作事实发生时间。
- 不通过增加 Cron 频率绕过失败信源治理。
- 不在本 Spec 前半段启用付费 Embedding、Reranker 或生成模型。
- 不因公开 Claim 总数超过 150 就立即切换 `live`。
- 不要求 OpenAI、Render、Cloudflare 或 SMTP 凭据通过聊天传递。

## 5. 统一指标合同

### 5.1 必须区分的 Claim 指标

以后所有页面和文档必须使用以下精确命名：

- `publicClaimCount`：公开快照当前返回的 Claim 数量。
- `entityLinkedPublicClaimCount`：绑定合法 `entityId` 的公开 Claim 数量。
- `approvedClaimCount`：审核记录状态为 `approved` 且不是 `merged-evidence` 的 Claim 数量。
- `humanReviewedClaimCount`：由真实管理员或审核员批准的 Claim 数量。
- `autoApprovedRelationClaimCount`：由允许的确定性关系规则自动批准的数量。
- `currentClaimCount`：生命周期为 `current` 的公开 Claim 数量。
- `historicalClaimCount`：生命周期为 `historical`、`superseded` 或 `retracted` 的可追溯数量。

正式 150 条门槛必须明确采用哪一个指标。推荐采用 `approvedClaimCount`，同时单独要求 `reviewedEvidenceRatio >= 90%`，不得用演示种子总数代替。

### 5.2 新增脱敏基线报告

新增管理员端点或扩展现有端点：

```text
GET /api/v2/admin/release-baseline
```

响应组合以下只读信息：

- 构建提交、服务发布标识、Alembic 版本；
- 公开数据统计和上述 Claim 口径；
- `/data-quality` 结果；
- `/golden-questions` 与 RAG 指标；
- `/review-queue-inventory` 汇总；
- `/operations` 心跳、最近周期、待抽取与冷却计数；
- 信源健康状态计数；
- 外部集成只返回是否配置和预检状态，不返回 Key、完整错误正文或连接串。

### 5.3 文档基线自动生成

新增只读脚本：

```text
python -m app.release_baseline --format markdown
```

脚本只接受管理员 API 返回的脱敏 JSON，生成中文基线表。README 只保留最新摘要和生成日期，详细历史写入独立基线文档。生成文件变化必须经过人工审阅，不允许 CI 自动提交。

## 6. 实施节点 A：真实运行基线与发布可追踪性

### 6.1 操作步骤

使用已有管理员会话依次读取：

```text
GET /api/v2/admin/production-readiness
GET /api/v2/admin/integrations
GET /api/v2/admin/operations?recentLimit=50
GET /api/v2/admin/review-queue-inventory
GET /api/v2/admin/data-quality
GET /api/v2/admin/golden-questions
GET /api/v2/admin/sources
```

仅保存计数、状态、时间和脱敏错误类型。不得把 JWT、Cookie、信源私密参数或供应商响应原文写入 Spec、日志或 Git。

### 6.2 发布标识改造

`/health` 和 `/ready` 增加：

- `buildCommit`：部署提交短 SHA；
- `schemaRevision`：当前 Alembic head；
- `builtAt`：构建时间；
- `release`：人类可读版本，仅作为辅助字段。

前端异常页和审核后台显示提交短 SHA，便于判断“代码已推送但 Render 尚未完成部署”。

### 6.3 验收标准

- 同一部署的 `/health`、`/ready` 和审核后台显示相同提交。
- 基线报告不包含任何 Secret。
- 能回答最近两个 Cron 周期是否触发、是否完成、是否部分成功。
- 能分别看到采集待处理、抽取待处理、抽取冷却和永久熔断数量。

## 7. 实施节点 B：Claim 实体关联与生命周期修复

### 7.1 处理顺序

对当前 27 条缺失实体的 Claim 执行只读分类：

1. `subject` 精确匹配实体 ID、slug、中英文名称或唯一别名：确定性回填。
2. 事实文本只命中一个实体规范名称：进入人工确认列表，不直接写入。
3. 同时命中多个实体或只命中系列名称：标记歧义，暂不进入当前公开视图。
4. 实体确实不存在：先登记实体和直接 Evidence，再关联 Claim。
5. 内容不是实体事实：拒绝或转为 Evidence/Timeline，不伪造实体。

### 7.2 写入规则

- 回填通过领域服务完成，记录操作者、理由、旧值和新值。
- 已公开 Claim 的关联修改必须生成发布历史。
- 不修改 Claim ID，不删除 Evidence，不覆盖审核历史。
- 新批准 Claim 必须有唯一 `entityId`，否则返回 `422`。
- 公共快照默认排除无实体、已撤回和已替代 Claim。

### 7.3 时间与生命周期

- 主时间继续使用 `validFrom → Evidence.publishedAt`。
- `reviewedAt`、`collectedAt` 只在来源详情中展示。
- 同实体、同谓词的新值必须选择“历史并存”“替代旧事实”或“冲突”，不能普通批准后同时作为当前事实。

### 7.4 验收标准

- `claimsWithMissingEntity=[]`。
- 新建无实体候选可以进入待审，但不能发布。
- 替代后旧事实只出现在历史查询，当前摘要和默认 RAG 不返回旧事实。
- 公开 Claim、Evidence、审核记录和发布历史数量可对账。

## 8. 实施节点 C：审核积压治理

### 8.1 队列分道

审核后台固定提供五个工作队列：

| 队列         | 条件                                                | 默认动作                     |
| ------------ | --------------------------------------------------- | ---------------------------- |
| 新鲜安全候选 | 30 天内、官方 Evidence、锚点完整、唯一实体、零冲突  | 优先人工批准或安全批处理     |
| 确定性重复   | 语义指纹与已发布或待审事实完全相同                  | 合并 Evidence，不新增 Claim  |
| 可能更新     | 同实体、同谓词、值不同或有效期相邻                  | 逐条选择替代、历史并存或拒绝 |
| 高风险与冲突 | 价格、可用性、Benchmark、安全、弃用、社区来源或冲突 | 强制人工审核                 |
| 无效与陈旧   | 缺 Evidence、无原文锚点、实体歧义或超过 90 天       | 补证据、明确拒绝或保持隔离   |

### 8.2 清理顺序

1. 先运行 Dry Run 并保存计数。
2. 先处理与已发布事实完全重复的候选。
3. 再处理待审队列内部的确定性重复组。
4. 再处理无 Evidence、无有效锚点和无法解析实体的候选。
5. 再处理可能更新组。
6. 最后处理冲突和高风险候选。

每批最多 50 条；每批结束重新运行 Dry Run，对账公开 Claim、Evidence、审核历史和发布历史。

### 8.3 自动批准边界

当前允许自动批准的六类关系仍保持：

```text
developed-by
based-on
benchmarked-on
uses
part-of
successor-of
```

扩大自动批准前必须满足：

- 连续人工复核样本不少于 100 条；
- 总体精度不低于 99%；
- 严重错误为 0；
- 仅使用第一方官方 Evidence；
- 主体、客体和关系语义都在同一原文锚点中；
- 实体唯一解析、零冲突；
- 仍保留每日抽样复核与一键关闭开关。

普通事实、价格、Benchmark、安全事件、弃用和冲突继续人工审核。

### 8.4 SLA

- 新鲜安全候选：48 小时内进入审核视野。
- 高风险候选：不自动批准，7 天内完成处理或记录等待原因。
- 确定性重复：每批处理后不增加公开 Claim。
- 超过 90 天的开放项必须有明确状态，不允许无限停留在普通待审。

## 9. 实施节点 D：信源失败、手动采集与自动熔断治理

### 9.1 信源状态矩阵

| 状态         | 含义                                 | 系统动作       | 人工动作                         |
| ------------ | ------------------------------------ | -------------- | -------------------------------- |
| `healthy`    | 预检和最近采集成功                   | 按信源周期运行 | 无                               |
| `retrying`   | 网络、429、502、503、504 等瞬时错误  | 有上限退避     | 观察，不重复点击                 |
| `paused`     | 永久错误连续达到阈值                 | 停止自动重试   | 更换入口或确认停用后重新排队     |
| `manual`     | 官网拒绝云服务器、社区页或不稳定页面 | 不自动抓取     | 通过可信机器入口或人工快照补充   |
| `unverified` | 尚未完成安全预检                     | 不启用自动采集 | 完成域名、体积、类型和稳定性预检 |

### 9.2 自动熔断信源

自动熔断不是“继续等待更多次重试”，而是配置修复任务：

1. 读取 `failureKind`，区分白名单、重定向、403、404、内容类型、体积和安全 DNS。
2. 检查证据地址与抓取地址是否应分离。
3. 优先登记同机构官方 Markdown、JSON、RSS、API 文档或原始仓库入口。
4. 所有备用入口分别执行同样的 HTTPS、白名单和公共 DNS 校验。
5. 新入口预检通过后手动重新排队一次。
6. 观察首次快照和第二个调度周期后再恢复长期自动采集。

不得通过清零失败次数让原错误地址继续无限重试。

### 9.3 手动采集信源

手动信源分为两类：

- **有官方机器入口**：保留原网页作为 Evidence URL，新增机器入口作为 `fetchUrl`，转为自动采集。
- **无稳定机器入口**：保持手动，只用于人工添加快照或证据；不伪装成自动更新。

手动信源不应阻止整个自动周期，也不计入“自动信源健康率”的分母。

### 9.4 OpenAI/GPT 获取方案

优先使用已经登记的官方机器入口：

```text
https://developers.openai.com/api/docs/changelog.md
https://developers.openai.com/api/docs/models.md
https://developers.openai.com/api/docs/deprecations.md
```

产品规则：

- Changelog 用于发现新模型、API 能力和行为变化。
- Models 用于核对模型 ID、能力和访问范围。
- Deprecations 用于核对弃用与下线，高风险人工审核。
- OpenAI 官网文章仍可作为 Evidence URL；若 Render 不能抓取，不反复请求官网首页。
- 新发现的官方文章只在机器入口 Diff 命中后进入候选生成，不扫描整个网站。

### 9.5 ERNIE 与重定向页面

- 预检必须记录最终 canonical URL。
- 如果重定向没有 canonical URL，先人工核对最终域名和内容，再更新证据地址。
- 同一文章 48 次失败不再继续普通退避，应进入 `paused/configuration`。
- 无稳定入口时保留人工快照，不降低 Evidence 来源可信度。

### 9.6 Hacker News 等社区来源

- 社区来源只用于发现线索和讨论，不作为高风险事实的唯一证据。
- 未进入自动白名单时保持手动是正确状态。
- 发现线索后必须回到官方发布、论文或代码仓库建立直接 Evidence。

### 9.7 是否增加信源

在以下条件全部满足前，不批量增加信源：

- 当前熔断和失败信源完成分类；
- 至少两个 Cron 周期成功；
- 新快照能进入抽取和审核队列；
- 去重没有重复制造候选；
- 审核队列的新鲜候选 SLA 正常。

之后每次只增加一个机构的一条机器入口，观察两个周期再继续。

## 11. 实施节点 F：零额外模型费用的 RAG 提升

### 11.1 先修数据，再调排序

在 27 条 Claim 实体关联和核心关系未修复前，不以调权重掩盖数据缺口。检索质量提升顺序为：

1. 重建 `rag_claim_documents` 投影并检查遗漏记录。
2. 将实体中英文名称、slug、别名和系列归属加入检索文档。
3. 建立问题词到谓词的确定性映射，例如“价格 → pricing”“上下文 → context-window”“谁开发 → developed-by”。
4. 对中文、英文和产品名分别计算字段权重。
5. 增加短词、型号和连字符归一化，例如 `GPT-5`、`GPT 5`、`gpt5`。
6. 当前、历史、弃用、发布时间问题使用不同生命周期和时间过滤。
7. 使用 PostgreSQL 全文排名与可选 `pg_trgm` 相似度召回，再做确定性重排。
8. 保持 SQLite 确定性降级，不假装与 PostgreSQL 排名完全一致。

### 11.2 排序建议

```text
综合分 = 0.30 × 全文相关度
       + 0.25 × 实体与别名精确命中
       + 0.15 × 谓词意图匹配
       + 0.10 × 官方 Evidence
       + 0.10 × 时间与生命周期匹配
       + 0.10 × Evidence 完整度
```

权重必须通过黄金问题验证，不允许只根据单个示例手工调到通过。

### 11.3 黄金问题分片

20 个黄金问题至少分为：

- 实体定义与归属；
- 版本与时间变化；
- 能力、规格和限制；
- 关系与路径；
- 对比与替代；
- 证据不足拒答；
- 历史、替代和撤回事实。

每条问题记录期望实体、可选期望 Claim、时间要求、来源类型、最小 Recall 和是否应拒答。

### 11.4 分阶段门槛

| 阶段         | 检索通过率 | 引用覆盖率 | 生命周期准确率 |       拒答准确率 |
| ------------ | ---------: | ---------: | -------------: | ---------------: |
| 当前         |        20% |       100% |           100% | 需管理员报告确认 |
| 词法检索可用 | 不低于 70% |       100% |           100% |             100% |
| RAG Ready    | 不低于 85% |       100% |           100% |             100% |

达到 70% 前不讨论 Embedding；词法检索仍无法解决的失败问题必须按“语义召回不足”与“知识库没有事实”分开统计。

## 12. 实施节点 G：付费 RAG 增强决策门

只有节点 F 完成后，才向用户提交一次费用决策，内容必须包括：

- Embedding 供应商和模型；
- 当前需要向量化的公开 Claim 数；
- 首次全量成本估算；
- 每日增量上限；
- Reranker 单次候选数和每日调用上限；
- 生成模型单次上下文、每日调用上限和失败降级；
- 数据保留与供应商隐私边界。

用户未确认前：

- `retrievalMode=lexical`；
- `answerMode=extractive`；
- Embedding、Reranker 和生成开关保持关闭；
- 不产生新增外部模型费用。

确认后也必须保持：

- 混合检索失败回退 lexical；
- Reranker 只能排序，不能创造事实；
- 生成结果逐句引用 Claim；
- Schema 或引用校验失败回退 extractive。

## 13. 实施节点 H：Live Gate 与外部生产保障

### 13.1 机器门槛

### 13.4 切换规则

切换后若 `/ready` 或数据质量失败，应回退 `demo` 或关闭公开正式读取，不删除已经审核的数据。

## 14. 自动化测试与质量规则

### 14.1 新增后端测试

- 发布无实体 Claim 返回 `422`。
- 确定性实体回填记录审计和发布历史。
- 歧义实体不会进入当前公开快照。
- 队列 Dry Run 不写数据库。
- 重复候选只合并 Evidence。
- 自动熔断不会继续领取采集租约。
- 更换安全机器入口后可以明确重新排队。
- 手动信源不计入自动健康率。
- RAG 投影重建数量与可公开当前 Claim 对账。
- PostgreSQL 中文、英文、别名、型号、时间和生命周期检索。
- 20 个黄金问题指标可重复计算。
- 健康接口返回构建 SHA 和迁移版本但不返回 Secret。

### 14.2 新增前端测试

- 基线指标使用精确名称，不混淆公开与人工审核 Claim。
- 审核后台五类队列筛选和计数正确。
- 新鲜候选默认优先于历史积压。
- 自动熔断和手动信源显示不同的下一步。
- 实体摘要最多 5 条，历史分页不重复不遗漏。
- 阅读模式在内容缺失时正确降级。
- RAG 诊断区分“没有知识”与“召回失败”。
- 构建提交在异常页和审核后台可见。

### 14.3 每批完整质量门禁

## 15. 发布、观察与回滚

### 15.1 发布顺序

严格按以下顺序实施：

```text
A 运行基线与构建追踪
→ B Claim 实体关联
→ C 审核积压治理
→ D 信源恢复与新鲜度
→ E 核心关系和展示
→ F 零费用 RAG

```

节点 A～F 不需要新增外部账号或模型费用，可以连续推进。

### 15.2 观察窗口

- 数据写入变更：至少观察一次公开快照刷新。
- 信源变更：至少观察两个 Cron 周期。
- 自动批准规则变更：至少完成 100 条人工抽样。
- RAG 排序变更：运行全部黄金问题，不以单题通过代替整体评估。

### 15.3 回滚原则

- 优先关闭新入口、自动采集或检索功能开关。
- 数据库只做向前兼容迁移，不删除审核、证据和发布历史。
- 信源回滚只停用新增入口，不删除已采集快照。
- RAG 回滚到 `lexical + extractive`。
- Live 切换失败时恢复 `demo`，不伪造质量报告。

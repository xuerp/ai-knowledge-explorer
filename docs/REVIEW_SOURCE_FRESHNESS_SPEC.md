# AI Radar 审核、信源与内容新鲜度治理 Spec

## 1. 背景

AI Radar 已具备安全采集、结构化抽取、候选事实、人审发布和公开知识库闭环，但真实运行暴露出五类相互关联的问题：

1. 审核后台曾出现整页加载失败，单个模块、旧缓存或异常历史数据不应拖垮整个工作台。
2. 待审核候选达到数百条后，全部逐条人工处理不可持续，新内容也容易被历史积压淹没。
3. 审核通过的事实全部平铺到实体页会形成信息堆积，用户难以先看到最新、最重要的变化。
4. 部分白名单信源预检或采集失败后长期重试，既不能获得新内容，也让后台出现几十次连续失败。
5. OpenAI 等官网会拒绝 Render 云服务器访问，单纯扩大白名单或反复预检无法解决及时更新问题。

本 Spec 将这些问题作为同一条数据供应链治理：**可靠发现 → 安全获取 → 增量抽取 → 风险分级审核 → 分层展示 → 运行告警**。

## 2. 目标与非目标

### 2.1 目标

- 定时自动任务每 30 分钟触发一次，但保持现有单周期抽取上限，不因提高触发频率而无限增加模型调用。
- 审核后台局部失败时仍可登录和使用其他模块，大型队列按范围和上限加载。
- 待审候选按新鲜度、风险、证据质量和是否适合批量审核进行排序与筛选。
- 低风险事实只在满足严格证据锚点、零冲突和唯一实体匹配时允许有限自动批准；高风险事实继续人工审核。
- 实体页默认展示最新事实，较旧事实进入可展开的历史归档，所有已审核事实仍然可查。
- 信源区分证据地址和实际抓取地址，支持官方 Markdown、JSON、RSS 或官方代码仓库等机器入口。
- 对失败进行分类，永久性失败达到阈值后自动熔断，瞬时失败继续有限退避重试。
- 为 OpenAI 增加可由 Render 访问的官方开发者机器入口，原始发布页面继续作为历史证据保留。

### 2.2 非目标

- 不绕过网站登录、验证码、付费墙、Cloudflare 防护或 robots 限制。
- 不把 Hacker News 等社区内容视为官方事实，也不允许社区传闻自动发布。
- 不为了去掉 Demo 标签提前切换 `AI_RADAR_DATA_MODE=live`。
- 不提高现有单周期模型抽取数量上限；任何进一步扩大模型用量的决策需单独确认。
- 不读取、输出或覆盖 `backend/.env` 中的任何凭据。

## 3. 核心产品规则

### 3.1 信源不是单一 URL

每条信源至少包含两层地址：

- **证据地址 `url`**：用户点击查看的原始官方页面。
- **抓取地址 `fetchUrl`**：后台实际读取的官方 Markdown、JSON、RSS、静态文档或同机构机器入口；为空时使用证据地址。
- **备用地址 `fallbackUrls`**：主抓取地址不可用时依次尝试的同一官方机构入口。

备用地址必须经过相同的 HTTPS、域名白名单、公共 DNS、内容类型和体积限制，不能成为 SSRF 或跨域跳转旁路。

### 3.2 失败分类与状态机

采集失败统一归为：

| 类别           | 示例                           | 行为                           |
| -------------- | ------------------------------ | ------------------------------ |
| `network`      | DNS、连接中断                  | 退避重试                       |
| `timeout`      | 连接或读取超时                 | 退避重试                       |
| `rate-limited` | HTTP 429                       | 退避重试                       |
| `upstream`     | HTTP 5xx                       | 退避重试                       |
| `blocked`      | HTTP 401/403                   | 尝试备用入口；持续失败后熔断   |
| `redirect`     | 跳转无目标、循环、超限         | 尝试备用入口；持续失败后熔断   |
| `allowlist`    | 域名不在白名单                 | 立即标记为配置问题，不自动绕过 |
| `content`      | 类型不支持、正文过短、体积超限 | 尝试机器入口；持续失败后熔断   |
| `unknown`      | 未分类错误                     | 有限退避并保留诊断             |

永久性失败连续达到 3 次后进入“已熔断”状态，不再每个周期重复请求；管理员更换入口或手动重新排队后解除熔断。瞬时错误不熔断，继续遵循最大退避时间。

### 3.3 社区信源

- Hacker News、论坛、社交媒体属于社区线索，不属于正式事实入口。
- 首页或搜索页不直接进入自动抽取；需要接入时应使用官方 API 或稳定数据接口。
- 社区候选默认高风险，不支持批量自动批准。
- 参数、价格、发布日期、基准成绩和可用性必须找到官方或原始评测证据后才能发布。

### 3.4 审核分级

候选审核级别由现有数据实时计算，不依赖模型自报置信度：

- **高风险**：存在冲突、缺证据、社区来源，或涉及价格、发布日期、上下文、可用性、状态、评测成绩等易变化字段。
- **标准风险**：有直接证据但不满足低风险自动规则。
- **批量安全**：待审核、零冲突、主客体均逐字出现在证据锚点中。

排序依次考虑：近期候选、高风险待判断项、证据发布时间、创建时间。旧候选不会删除，但可以按“历史/陈旧”筛选集中处理。

### 3.5 发布与实体展示

- 审核通过的 Claim 会进入公共知识库，但不等于必须在实体首屏全部展开。
- 实体页默认展示最近核验的 5 条事实，每条 Evidence 默认折叠。
- 其余事实放入“历史事实”折叠区，前端每次加载 10 条，仍可查看、引用和用于研究问答。
- 时间线继续负责呈现版本演进；重复语义事实在进入审核队列前去重。
- 未来如单实体事实继续增长，可在 API 增加分页，而不是删除历史证据。

## 4. OpenAI 与典型失败信源方案

### 4.1 OpenAI

保留 `openai.com/index/...` 等历史发布页面作为证据；新增以下官方开发者入口用于持续更新：

- API Changelog Markdown：发现模型和 API 变化，2 小时检查一次。
- Models Markdown：发现当前模型能力与规格变化，4 小时检查一次。
- Deprecations Markdown：发现弃用和下线信息，24 小时检查一次，高风险人工审核。

这些入口使用 `developers.openai.com`，加入精确白名单；内容未变化时依靠 ETag、Last-Modified 和内容 Hash 跳过抽取。

### 4.2 文心 ERNIE

“预检曾通过但采集返回无目标跳转”归为 `redirect`。系统先尝试官方备用入口；连续 3 次仍失败则熔断，避免出现 48 次无效重试。找到新的百度官方规范地址后由管理员更新抓取入口并重新排队。

### 4.3 Hacker News

保持非白名单和手动状态。若未来建设社区雷达，应新建独立的社区发现器并使用官方 API；这不属于本轮正式知识采集入口。

## 5. 审核后台可靠性

- 管理路由不进入 Service Worker 页面缓存，避免旧前端壳与新 API 不兼容。
- 工作区各模块独立加载，单个接口失败显示局部告警，其他模块继续可用。
- 审核队列拆成“开放项”和“最近历史”两个有上限请求：开放项最多 500 条，历史默认最近 100 条。
- 后端支持 `scope=open|history|all` 和 `limit`，避免每次登录传输全部历史证据正文。
- 登录过期与网络失败分开处理；只有明确的 401 才清理会话。

## 6. 定时任务和费用控制

- Cloudflare Cron 使用 `17,47 * * * *`，每小时两次。
- Cron 只是唤醒自动化，具体信源仍按各自的 2～24 小时周期判断是否到期。
- 抓取与 Hash/Diff 不产生外部模型费用。
- 只有新快照进入抽取，且继续受现有“每周期最多 2 个快照、每快照最多 10 个候选”限制。
- 因此提高唤醒频率主要缩短等待时间，不等于把全部信源每 30 分钟重新抽取。

## 7. 数据结构和接口变更

### 7.1 `sources` 新字段

- `fetch_url`：可选实际抓取入口。
- `fallback_urls_json`：备用官方入口列表。
- `last_successful_fetch_url`：最近成功使用的入口。
- `failure_kind`：最近失败分类。
- `auto_paused_at`：因永久性失败自动熔断的时间。

### 7.2 管理 API

- 创建、更新信源支持 `fetchUrl` 和 `fallbackUrls`。
- 信源响应增加有效抓取入口、备用入口、失败类别和健康状态。
- 预检和立即采集按主入口、最近成功入口、备用入口的安全序列执行。
- 重新排队会解除自动熔断并清除旧失败状态。
- 审核队列增加范围和数量参数。

## 8. 验收标准

### 8.1 自动化测试

- 主入口失败、备用入口成功时产生快照并记录成功入口。
- 备用入口仍必须通过白名单和公共 DNS 校验。
- 永久性错误连续 3 次后自动熔断，瞬时错误不熔断。
- 手动重新排队可以解除熔断。
- OpenAI 官方 Markdown 内容类型可被安全抓取。
- 审核队列 `open/history` 范围与数量限制正确。
- 数百条审核数据不会要求一次传输全部历史。
- 实体事实按更新时间倒序，默认 5 条，其余进入历史归档且每次加载 10 条。
- 管理路由不被 PWA 导航回退缓存。
- Cron 表达式和调用次数测试保持每小时两次。

### 8.2 完整质量门禁

严格执行 `.github/workflows/quality.yml`：

1. `bun install --frozen-lockfile`
2. 导出演示快照并确认无差异
3. `bun run check`
4. Cloudflare staging 配置生成验证
5. Ruff 格式、Lint 和 Python compileall
6. SQLite Alembic upgrade/current/check
7. PostgreSQL Alembic 验证（本地服务可用时）
8. 后端完整 pytest

## 9. 上线顺序与回滚

1. 先发布数据库向前兼容迁移和 API。
2. 再发布前端状态展示、队列筛选与事实归档。
3. Render 新版本健康后，由种子目录登记 OpenAI 机器入口；管理员通过一次“批量安全接入”完成预检、启用和首次采集后进入自动调度。
4. 观察至少两个 Cron 周期，确认新快照、失败分类、抽取上限和审核队列正常。
5. 如出现异常，仅停用新增信源或关闭其自动采集；证据数据、旧快照和审核历史不回滚、不删除。

## 10. 完成定义

本轮完成不以“所有历史候选全部审核”为标准，而以下列可持续能力为标准：

- 新内容不再被旧积压阻塞；
- 永久失败不再无限重试；
- OpenAI/GPT 有可持续官方入口；
- 高风险人工审核、低风险有限自动化的边界清楚；
- 实体页信息可读且历史完整；
- 后台局部故障不再导致整页不可用；
- CI 绿色且线上健康检查正常。

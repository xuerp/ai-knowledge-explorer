## 简历项目

**AI Radar｜基于证据的 AI 技术研究与选型平台**

React、TypeScript、TanStack、FastAPI、SQLAlchemy、SQLite / PostgreSQL。

- 围绕 AI 技术追踪与选型，设计动态、知识库、模型家族、结构化对比、决策研究和知识图谱的跨页面流程。
- 建立 Entity–Claim–Evidence 数据模型，将对象、事实、来源与审核状态分离，支持来源摘录、时间信息和历史版本追溯。
- 实现前后端目录一致性校验、候选审核与个人研究持久化；将公共知识和用户活动分开，避免演示记录混入真实使用结果。
- 排查来源 URL 导入缺陷，恢复 60 条已获取成功的原始来源地址，并建立来源保真和公开快照回归。
- 实现并复验登录、需求提交、研究保存与修改、历史重开及 Markdown/PDF 导出，区分官方功能依据与未经实测的性能结论。

按本人实际参与范围调整动词和职责。可说“本地目录保留 262 个实体、462 条事实记录”，不能把记录数量写成全部已验证的数据规模，也不添加用户量、成本收益、准确率或生产 SLA。

## 90 秒介绍

AI Radar 解决的是 AI 技术信息散落、版本变化快、选型判断缺少依据的问题。用户先从动态发现变化，再进入知识库核对模型版本、适用条件和来源，也可以带着任务进入决策研究。底层把对象、事实和证据分开，候选资料经过审核才进入公共知识，个人研究记录通过账户接口保存。

项目用 React 和 TanStack 组织前端流程，用 FastAPI 和 SQLAlchemy 提供业务接口与持久化。我重点讲清楚数据一致性、证据边界和故障定位。例如，导入脚本曾删除文档网址的 `.md` 后缀，修复时不仅恢复链接，还增加回归，防止下一次导入再次破坏来源。目前完整目录保留，来源检查和产品验收仍有缺口，未将历史评测包装成当前模型效果。

## 面试追问

**为什么不直接做聊天界面？** 研究需要保留可复用的对象、事实、来源、历史与审核状态，聊天只是其中一种入口。

**怎么核实数据？** 分开检查链接获取、原文摘录、陈述语义和时效。抓取成功不等于事实正确；检查失败也不能直接判定事实为假。

**怎么处理示例数据？** 示例问题是编辑提供的输入提示，明确标注；公共页面不展示预写研究答案、模拟关注和通知。真实个人活动从账户接口读取。

**有哪些取舍？** 保留完整产品和目录，逐项修复数据，避免用缩小数据范围制造完成感。缺少成本、性能或可用性证据时保留未知，不生成无依据的排名。

**还有什么没完成？** 以[来源核实记录](CATALOG_VERIFICATION_20261026.md)和[研究流程复验](WORKFLOW_VERIFICATION_20261026.md)为准。研究主流程已有本地浏览器验证；全量来源语义、其他产品流程及真实模型效果仍不能由构建和单元测试代替。
